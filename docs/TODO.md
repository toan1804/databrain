# Known gaps to fix later

Found in reviews and left for a later release on purpose. Each says what goes wrong; remove an entry when it is fixed.

## Single program (verify on Windows before relying on it)

- An update while an MCP client is connected: the installer may end the MCP session (`databrain.exe mcp`), or hit "file in use" on the `databrain-mcp.exe` launcher.
- If an MCP client kills `databrain-mcp.exe` without closing its stdin, the child `databrain.exe mcp` may keep running (no job object ties them).
- `databrain-jobs run` / `list` output in a terminal goes through the GUI-subsystem launcher's console attach; check it prints in cmd and PowerShell.

## Connector core (review of 2026-11-12; see [CONNECTOR_CORE.md](CONNECTOR_CORE.md))

Every finding of the review was fixed on 2026-11-13, with the never-read corpus and the whole-vs-pieces property (`crates/connector-core/tests/classify_corpus.rs`), tri-state `Session::transaction_state` with the unused `Capabilities` fields removed, keyword and positional secrets in redaction, and one scanner for strings and comments (`skip_token`). A `Session::supports(Feature)` enum wasn't added: the optional features already say "not supported" through their own return values (`object_versions` → `None`, `check_sql` → `false`). The redaction functions keep their own, dialect-free lexing on purpose: they scrub any text (history, logs, error messages) without knowing its database. Since 2026-11-14 the SQL secret rules read one tokenizer in six readings, sessions run only `Checked` statements or `Statement::internal` SQL, and each statement is parsed once (`ParsedStatement`); the splitter stays the authority on where statements end, so a gap in sqlparser's tokenizer can't become a split failure.

Idea still open:

1. **Function allow-list for reads** (medium; a product decision). Unparsed text, hidden statements and the acting-function list are covered; left is treating a SELECT that calls a function outside the built-in list as `Unknown`. Only SQL Server (functions can run extended procedures) and Oracle (autonomous-transaction functions) need it, and there it would refuse many ordinary reads on read-only connections (`regexp_count`, `sys_context`, `dbms_lob.substr`, any user function) until the built-in lists are complete. The AI path already asks about such functions (`unknown_functions`).

## AI assistant (review of 2026-11-14)

The review's privacy gaps and bugs were fixed on 2026-11-15 (a connection's rules hold wherever it is reached from, jobs are reviewed again when they run, the row cap, stream errors, the job tools' silent fallbacks). Left:

- **Tool arguments are read from loose JSON.** The job tools now refuse a schedule or an export format they can't read, but the other tools still take each field by hand (`args.get(..)`), with undocumented aliases (`insert`, `upsert`, `mirror`). Typed structs (`deny_unknown_fields`) that also produce the schema sent to the model would remove the class.
- **Table rules know only the first schema of a `search_path`**: see "Table rules check unqualified names under the first schema only" in the review of v0.4.1..main below, which also covers SQL Server and the lookup failing open. Not yet checked live on SQL Server, Snowflake or Databricks.
- **PII rules follow tables, not views.** A view over a masked column is another table to the rules: only a rule without a table (`email`) masks it.
- **Notes about dropped or renamed tables stay** (hidden from the model, never removed), and there is no limit on the number of notes or proposals.
- **A schema that becomes empty keeps its tables in the AI's catalog** until the next full index (not confirmed; `kn_replace_schema_read` with an empty list).
- **Workspace SQLite on the async runtime**: `knowledge::retrieve` and a schema's index write run on the runtime's threads; a learn pass commits once per sighting.
- **Providers**: the OpenAI-compatible stream is still read as complete when it ends without `[DONE]` or a finish reason (some local servers end that way); Gemini's `thoughtSignature` is not kept with a tool call (newer models may want it back; not confirmed); the SSE reader has no cap on one line or one event; inline completions cancelled before the first byte are counted as zero tokens.

## Connectors (review of 2026-11-15)

Fixed on 2026-11-15: catalog queries built with a literal a backslash could end (MySQL, Snowflake, Databricks, Redshift, Postgres, BigQuery paths), the crashes on text outside ASCII (MongoDB, Neo4j), Databricks running a write twice, `results.<name>` hidden behind a comment, and the DuckDB sandbox writing into attached folders. Left, most serious first:

**Stop and the row limit**
- **Oracle:** Stop during a large fetch drops a half-read frame from the helper; the session is then dead or hangs (`oracle/src/exec.rs`, `Agent::read` is not cancel-safe). One reader task owning the helper's output would fix the class. A statement cancelled while it waits for the session still runs (both drivers).
- **MySQL:** cancel waits on the connection mutex its own statement still holds when the kill fails or takes more than 10 s: the session blocks for good (`mysql/src/session.rs`). A cancel during row streaming often sends no `KILL QUERY`.
- **MySQL, SQL Server:** the row limit inside `CALL p()` / `EXEC p` abandons the rest of the procedure and reports success. Only classified reads should be abandoned.
- **Postgres:** inside a transaction the row limit reads the whole result to its end before finishing; a cancel that races a ready row is not sent to the server.
- **SQLite, DuckDB, Oracle (thick):** cancelling a statement that waits for the session interrupts the one that is running, and the cancelled one then runs.
- **MongoDB, Neo4j:** cancel and the row limit only drop the local future; the server keeps working. **ClickHouse** relies on the server noticing the closed response.
- **Snowflake, BigQuery, Databricks:** a failed poll returns the error without cancelling the query on the server. Snowflake's submit URL carries two `requestId`s (the abort sends the first; which one the server uses is not confirmed). BigQuery polls and cancels with the configured location, not the job's.

**Wrong results or state**
- **Oracle:** `create … procedure` whose `end;` starts a line loses its final `;` (`prepare_sql` looks for `" END"`); a thick read-only session reads as of connect time; the thin read-only transaction may reconnect per statement (not confirmed); materialized views list as tables; `RAW` shows as `RAW(0)`; `DBMS_OUTPUT` is not read.
- **Postgres, MySQL:** `transaction_state` is wrong after a failed `COMMIT` (Postgres observes the text before running it) and after DDL commits implicitly (MySQL).
- **SQL Server:** `decimal(18,0)` shows as `12345.0`, `datetime` fractions are truncated, `money` goes through a float, `datetimeoffset` loses its offset; the `Prefer` fallback to no encryption never runs (tiberius returns an error, the code expects a panic); a database named `a.b` is split wrongly in all-databases mode.
- **ClickHouse:** an exception mid-stream in a one-column result is shown as a row.
- **MongoDB:** options the shell parser doesn't know are dropped (a `collation` on `deleteMany`), `deleteMany()` without a filter deletes everything, integers above 9.0e15 lose digits; `mapReduce` with an `out` document and `createCollection … viewOn` don't report the collections they touch.
- **Neo4j:** durations and temporal values inside lists or maps are shown wrongly; a Cypher `\uXXXX` escape could hide a write keyword from the classifier (server behaviour not confirmed).
- **SQLite:** a value that doesn't match its column's declared type shows as NULL; `max_rows` is not read; tables named `sqlite?…` are hidden (`_` is a LIKE wildcard).
- **DuckDB:** attached-file views are created in the user's database (`files` schema), which fails on a read-only file and persists views in a writable one; a hostile `.xlsx` can use unbounded memory; `RETURNING` after a newline is not seen; Decimal256 outputs load as DOUBLE; one file can be opened twice (read-only and read-write); an output loaded inside a rolled-back transaction is remembered as loaded. A view the assistant made over `results.<name>` in one chat can be read by another chat on the same sandboxed instance.
- **Databricks:** catalog reads are cut at 100,000 rows without notice; BINARY shows in three forms.

**Connections and secrets**
- **TLS:** Postgres and MySQL `Prefer` falls back to plaintext, `Require` accepts any certificate (as libpq does); MySQL's fallback also triggers on a wrong password. Only `VerifyFull` verifies; there is no CA-file option.
- **Hosts are not validated** (Snowflake account, Databricks host): `evil.com/a` or `host@evil.com` sends the credential elsewhere; an imported connection is the realistic route. Snowflake's presigned chunk URL can appear in an error message.
- **SQL Server and MySQL keep the credential** for reconnects (an Entra token expires after about an hour).
- **Oracle:** the Instant Client install uses a predictable folder in a shared `/tmp` on Linux; `DATABRAIN_ORACLE_AGENT` runs an unverified helper; the helper keeps running a statement after DataBrain dies.
- **Redshift read-only** rests on `SET SESSION CHARACTERISTICS … READ ONLY`, which may be a no-op there (not confirmed).

## Review of v0.4.1..main (2026-11-15)

A review of the 54 commits since v0.4.1 (PRs #40–#53). Findings were checked on main at 2ab9270 unless the entry says otherwise. Each says where, what goes wrong, and the fix the review suggests.

**Fix before the next release**

1. **DuckDB sessions share one spill folder** (`connectors/duckdb/src/engine.rs` `session_settings`). Every in-memory instance (each tab, the Results connection, the jobs runner, MCP) sets the same `temp_directory = <app data>/duckdb_spill`. DuckDB's temp file names repeat in every instance (`duckdb_temp_storage_<size>-<n>.tmp`, `duckdb_temp_block-<id>.block`) and are opened without an exclusive create; closing an instance deletes every `duckdb_temp_*` file in the folder. Two tabs that spill at once (large sorts or `GROUP BY`s) can overwrite each other's blocks (wrong answers or corrupt-block errors), and closing one deletes the other's files mid-query. Traced in the DuckDB 1.5.6 source, not reproduced. Fix: a folder per instance (`duckdb_spill/<pid>-<n>`, as `sandbox_spill_dir` does for the sandbox), stale ones removed at start; a test with two instances spilling at the same time.
2. **Table rules check unqualified names under the first schema only** (`query-engine/src/metadata.rs` `default_namespace`, `ai/src/access.rs` `defaults`). The rules use Postgres `current_schema()` and SQL Server `schema_name()`, but Postgres walks the whole `search_path` and SQL Server falls back to `dbo`. With `search_path = hr, public` and a rule denying `public.salaries` (the table exists only in `public`), `select * from salaries` was denied before #51 and now runs; an allow-list such as `%.hr.%` lets every `public` table through an unqualified name. When `default_namespace` fails or times out, `learn_defaults` silently keeps `public`/`dbo`: fail-open. The live test creates the table in both schemas, so it can't catch this. Fix: when Postgres `current_schemas(false)` has more than one entry, or SQL Server's schema isn't `dbo`, mark the schema as ambiguous so unqualified names are refused (plain `None` falls back to the usual default); do the same when the lookup fails on a connection with rules. Or resolve each name on the server (`to_regclass`, `OBJECT_ID`).
3. **Scheduled AI job steps are checked with the wrong schema** (`app/src/jobs.rs` `ai_rules_now`). The run-time review reads the process-wide `LEARNED` cache but never fills it; `databrain-jobs tick` is a new process every minute, so it always assumes `public`/`dbo`, and in the app the cache can be stale. A step `select * from pay` on a role whose `search_path` is `hr`, with a later rule `read_deny %.hr.%`, passes and reads `hr.pay`. Fix: call `access::learn_defaults` for the step's connection and load target before `review_step`.
4. **Manual commit can autocommit on SQL Server and Snowflake** (`query-engine/src/sessions.rs` `needs_begin`, `connector-core/src/conn_state.rs` `observe`). `needs_begin` skips BEGIN when the state is `Unknown`, which means only that the `implicit` flag is set. `observe` sets it from any `AUTOCOMMIT` / `IMPLICIT_TRANSACTIONS` word followed by a value, in any statement and inside strings and comments (quotes are read as spaces). `select * from audit where note = 'autocommit off'` followed by `update … where id = 1` sends no BEGIN; Snowflake commits the update at once, while the UI shows a Rollback that undoes nothing. Fix: read the setting only from `SET …` / `ALTER SESSION SET …` code words, or ask the server (`@@OPTIONS & 2`, `SHOW PARAMETERS LIKE 'AUTOCOMMIT' IN SESSION`) before skipping BEGIN; a test with a false signal followed by a write.
5. **A password after `E'\''` and a `"name\"` is kept** (`connector-core/src/sql/redact.rs` `Reading::ALL`). Since 016a473 the backslash reading also escapes inside `"…"`, and the old reading (backslash escapes in `'…'` only, as Postgres and DuckDB read text) is gone. `select e'\'' as "c\"; alter role r password 'pw1' -- "` keeps `pw1` in history, job logs and the audit log; the code before 016a473 hid it. Fix: separate backslash flags for `'` and `"`, keeping both the old and the new combination; this text as a test.
6. **Redaction is quadratic on repeated `sp_*` names** (`redact.rs` `positional_secrets`). `open.iter().any(|c| c.parens)` runs for every procedure name and the stack of open calls grows without limit: `"sp_password ".repeat(n)` takes 0.2 s at 10k, 0.7 s at 20k and 2.9 s at 40k repeats (release build). This makes `long_repeats_stay_linear` flaky (27.6 s against its 20 s limit when the whole suite runs). Fix: a count of open paren calls, or no new procedure pushed while one is open; add the input to the redaction bench.
7. **ClickHouse lake table functions count as reads** (`connector-core/src/sql/classify.rs` `CLICKHOUSE_EXTERNAL`). `iceberg`, `icebergS3`, `icebergAzure`, `icebergHDFS`, `icebergLocal`, `icebergCluster`, `deltaLake`, `deltaLakeCluster`, `hudi` and `hudiCluster` (consider `arrowflight`) are missing, so `select * from iceberg('https://b.s3.amazonaws.com/t/', 'k', 's')` is a Read that read-only connections and the AI allow. Their key arguments aren't in `POSITIONAL_SECRETS`, so they aren't redacted.
8. **The table-rules live tests never run in CI** (`app/tests/table_rules_live.rs`). They aren't `#[ignore]`d and return early without `DATABRAIN_<DB>_HOST`, while the live job runs only ignored tests (`.github/workflows/ci.yml`, `-- --ignored`). They pass empty in the normal jobs and are skipped in the one with servers, including the search-path test and the MySQL `\'` canary. Fix: `#[ignore = "live: needs DATABRAIN_<DB>_HOST (cargo test -- --ignored)"]`, as ADDING_A_CONNECTOR §6 says.
9. **A DuckDB write can run twice** (`connectors/duckdb/src/exec.rs`, the retry after DuckDB interrupts itself). The statement is re-run to report the real error when its first word is `SELECT|WITH|FROM|VALUES|TABLE`; DuckDB accepts `WITH … INSERT/UPDATE/DELETE`. If the first run fails on a transient error (out of memory, temp disk full) and the re-run succeeds, it commits while the user is told to run it again, which inserts the rows a second time. For plain reads the retry runs the whole query again, fully in memory. Fix: retry only statements the engine classified as reads (pass it in `ExecOptions`), or drop the retry.

**Should fix**

- **DuckDB `memory_limit` is per instance** (`app/src/api/outputs.rs` `duckdb_memory_limit`). Every instance gets RAM − results budget − floor (about 10.4 GB on a 16 GB machine), so several tabs can promise more than the computer has. The CHANGELOG entry for #41 says the two can't. Share one limit, divide it by the live instances, or correct the claim.
- **Result spill files survive quit** (`app/src/lib.rs` `RunEvent::Exit`). Exit only persists the active outputs; unmasked Parquet stays under `results_spill/` until a DataBrain process starts again, and `duckdb_spill` is never cleaned. Remove this process's folders on exit (app, jobs runner, MCP); say what remains after a crash.
- **Disk use on spill has no budget.** `low_disk` stops only the result that is loading and `enforce_budget` counts memory only, so a few big queries leave 1–4 GB free and every later result stops; older results on disk are never freed for space. Evict the least recently used inactive results on disk when `low_disk` trips, or cap the total spill size.
- **The first move to disk holds the result's lock** (`query-engine/src/run.rs`, `spill_to` under `rs.lock()`). Up to half the budget (up to 8 GB) of Parquet is written under the lock, and the async commands `list_outputs`, `get_output` and `result_info` block runtime workers on it. Write the existing batches from a snapshot outside the lock, then swap in the spill.
- **The AI scope cleared on a server change grows back** (`workspace/src/meta_cache.rs` `meta_check_identity`). It deletes `ai_scope` but keeps `ai_policy.index_schemas`; the next "Index for AI" uses that list without asking and `put_rule_if_absent` allows each indexed schema again (every non-system schema with `*`). Clear `index_schemas` too, or make the next index ask; a test that indexes after the move.
- **Provider rules check only the connection a chat began on** (`ai/src/agent.rs`). Connections reached in earlier turns (a tool's `connection`, an @mention, an output's source) aren't recorded, so their rows in the history can go to a provider those connections don't allow when the chat switches provider; the check is skipped when the first connection was deleted. Record every connection whose data entered the session and check them all, or pin the provider per conversation.
- **The sandbox's own spill folder is set fail-open** (`connectors/duckdb/src/sandbox.rs`, `let _ = … SET temp_directory`). On failure the sealed instance keeps the shared folder, which `lock_configuration` then fixes in place. Return the error, or check `current_setting('temp_directory')` before locking.
- **SQL Server lock hints are reads** (`classify.rs` `pre_visit_query`). `select * from t with (updlock)` and `with (xlock, holdlock)` classify as Read, while `FOR UPDATE` on Postgres, MySQL and Oracle doesn't. Check `TableFactor::Table { with_hints }` for `UPDLOCK`, `XLOCK`, `HOLDLOCK`, `TABLOCKX`, `SERIALIZABLE`, `REPEATABLEREAD`.
- **`EXEC` doesn't trigger the `@@TRANCOUNT` check** (`conn_state.rs` `may_change_depth`). A procedure that opens a transaction and returns leaves the tracked state `None` with a transaction open on the server (its error 266 arrives while `in_transaction()` is false), so the session counts as replaceable and the work can be rolled back silently. Add `EXEC`/`EXECUTE`, or sync on every failure.
- **The ER cache keeps dropped foreign keys** (`workspace/src/meta_cache.rs` `meta_put_schema_tables`). An empty key list keeps the cached keys (`coalesce(excluded.fks_json, …)`), so a key dropped on the server stays in the offline ER diagram and the AI's joins; 20a91c4 fixed the same for index runs. Replace the keys when the read includes them.

**Smaller**

- The on-disk notice (`run.rs` `on_disk_notice`) still says sorting and filtering read from disk; since 0258ea8 they apply to the first rows loaded in the grid. It reaches the AI too.
- The AI's `query_outputs` advice (`ai/src/tools/query.rs`) says DuckDB reads the files "without loading them"; in the sandbox every row is copied into an in-memory table that also spills, unchecked by `low_disk`.
- Excel import silently drops end blocks with under 5% of the cells after a 3-row gap (`connectors/duckdb/src/xlsx.rs` `table_span`); the only trace is a SQL comment. Show `left_out` as a notice or in the import dialog.
- Two stop messages name the wrong cause: the u32 row-id cap says "Increase the row limit", and a spill refused for low disk blames the memory a result may keep.
- MySQL loads: the implicit-commit check reads the first two whitespace words (`query-engine/src/load.rs`), so a comment before `SET PASSWORD` hides it and `SET autocommit = 1` (which commits) is treated as harmless. Use `code_words`.
- macOS free memory (`app/src/sysmem.rs`): `mach_host_self()` is called on every read and its port reference never released; speculative and purgeable pages are left out, so free memory reads low and results go to disk early.
- Each statement of a script keeps at least 4 MB that is never evicted (`run.rs`, `.max(4 << 20)`), so N statements can keep N × 4 MB.
- The `get_array_memory_size` entry (buffers shared between batches counted once per batch) was removed from this file in #45 without a fix.
- Closing a chat races its cancelled run (`aiCancel` and `aiLeaveSession` aren't ordered), so outputs of a statement that finishes after `leave_tab` stay active.
- `SessionRole::is_ai()` is never used: nothing checks that AI or MCP SQL runs on an AI-role session key.
- Redaction doesn't know Databricks raw strings: `options (password r'pw')` is kept.
- `ui/tsconfig.tsbuildinfo`, a build artifact, is committed (changed in 4529fa5).
- Pre-existing, unchanged since v0.4.1: `redact_url_passwords` is quadratic (`"a://b:c ".repeat(n)`: 9.2 s at 80 KB); secrets inside MySQL `/*! … */`, after a Postgres nested comment that hides a quote, after MySQL `5--1`, behind `_utf8mb4'pw'`, and in procedure arguments after a comment or a line break are kept.
