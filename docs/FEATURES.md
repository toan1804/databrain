# DataBrain features

Detailed reference for what DataBrain does. For an overview, see the [README](../README.md).

- **Connections:**
  - Databases: SQLite, PostgreSQL, MySQL/MariaDB, SQL Server, Oracle, Snowflake, Databricks, BigQuery, and DuckDB for local files.
  - Amazon Redshift (provisioned and Serverless): a PostgreSQL connection with Database type "Amazon Redshift" (set by itself for `*.redshift.amazonaws.com` / `*.redshift-serverless.amazonaws.com` hosts and DataGrip/DBeaver Redshift imports; port 5439). The explorer, DDL (`SHOW TABLE` / `SHOW VIEW` / `SHOW PROCEDURE`), columns with their informational keys, completion and query hints (distribution key and style, sort keys, row count) use Redshift's catalog. Sign-in with a password, or "IAM (AWS CLI)": each connect gets a temporary password from the AWS CLI (`get-cluster-credentials-with-iam`, `get-cluster-credentials` when a Database user is set, or `redshift-serverless get-credentials`), so profiles, SSO, MFA and assumed roles work as in the CLI; the cluster or workgroup and region come from the host unless set. An expired temporary password is fetched again and the connect retried once.
  - ClickHouse: over the HTTP interface (8123, or 8443 with TLS for ClickHouse Cloud); a host starting with `https://` or SSL mode Require/Verify turns TLS on. Each tab is a ClickHouse session, so `SET`, `USE` and temporary tables carry over between statements; Stop kills the query on the server. The explorer lists databases with their tables, views, materialized views and external-engine tables (row counts, comments, `CREATE` DDL), and query hints show the primary, partition and sorting keys and data skipping indexes. A read-only connection runs with `readonly=2`. ClickHouse is not a load target for jobs yet. DataGrip and DBeaver ClickHouse connections import (native ports 9000/9440 become 8123/8443).
  - MongoDB: host and port or a connection string (`mongodb+srv://…` for Atlas). The explorer lists databases and their collections and views; describing a collection samples 200 documents to list its fields and types, and Show DDL gives `createCollection`/`createIndex` commands. Queries are mongosh-style, one command per run (`db.orders.find({status: "A"}).sort({at: -1}).limit(10)`, `aggregate`, `countDocuments`, `distinct`, `insertOne`/`updateMany`/`deleteMany`…, `db.runCommand({…})`, `use shop` on the first line), with `ObjectId(…)`, `ISODate(…)` and relaxed JSON, or a JSON database command (`{"find": "orders"}`). Documents come back as rows: top-level fields are columns (types inferred from the first 1,000 documents), nested documents and arrays are JSON text, so they work with outputs, DuckDB joins, export and the AI like any result. Writes ask first like SQL writes.
  - Neo4j: host and port or a URI (`neo4j+s://…` for Aura). The explorer lists node labels (Nodes) and relationship types (Relationships) with their properties, counts, and constraints/indexes as DDL. Queries are Cypher; columns follow the `RETURN` order, and a returned node or relationship is shown as its properties (`_id`, `_labels`, then each property).
  - MongoDB and Neo4j are not load targets for jobs (save to a file or load into another database instead), and lineage, Format and SQL completion are for SQL connections only.
  - Sign-in: passwords/tokens/keys go in the OS keychain. Browser sign-in (OAuth PKCE, Snowflake SSO), device code, service principals, service accounts, and CLI logins (gcloud, Databricks CLI, az).
  - SSH tunnels with host-key pinning.
  - Test fails fast: a DNS + TCP check tells "unknown host", "connection refused" and "no answer" apart within seconds, the whole attempt gives up after the connect timeout (Settings → Queries → Connecting, default 20 s; browser sign-in is not limited), and Stop cancels it. The same limit applies whenever a tab, the explorer, the assistant or a job opens a session on a server, so a server that accepts the connection and never answers fails with a message instead of a spinner; downloading the Oracle thin driver on first use and local files are not counted. A failed test's error can be copied, and "Ask AI" explains it and what to change, right in the dialog (the settings are sent without passwords or keys; the conversation stays in the AI panel).
  - Folders with drag and drop. Right-click empty space in the explorer for New connection, New folder and Query a local file.
  - Import and export: right-click empty space in the explorer (or the palette) → Import connections… reads DBeaver's `data-sources.json` (hosts, users, SSH tunnels, folders, prod/test tags; users and passwords from the `credentials-config.json` next to it unless DBeaver has a master password; URL-only connections from their URL), DataGrip's data sources (the newest DataGrip's global `options/dataSources.xml`, or a project's `.idea/dataSources.xml`: JDBC URLs for Postgres, MySQL/MariaDB, SQL Server, Oracle, Snowflake, Databricks, BigQuery, SQLite, DuckDB, MongoDB; users from `dataSources.local.xml`, groups as folders, read-only; passwords and SSH tunnels stay in DataGrip), `~/.pgpass` (with its passwords) or a DataBrain export. Passwords go to the keychain. It lists them with the ones already here marked and saves those you pick, also when something is missing (a user, a password, a project): the list says what to fill in after. Export connections… writes every connection (folders, environment, settings, AI rules) to a `.databrain-connections.json` file without passwords or keys; a password inside a connection string is removed.
- **Explorer:** three-level engines (Databricks, Snowflake, BigQuery, DuckDB) show catalog → schema → tables, catalogs first: a catalog's schemas are listed when it opens. SQL Server connections without a database work the same way: every database the login can open is listed (user databases first, `model` and `tempdb` left out), and tables are named `database.schema.table`; with a database set, only that database is shown, as before (Azure SQL Database can't query across databases: set the database there).
  - Cached locally (app-data SQLite): catalogs, schemas, tables and columns you have seen show at once on the next start, before connecting, and stay browsable offline ("Offline · cached 2 h ago"; completion uses the same cache).
  - On connect, one fingerprint query per connection tells which cached schemas changed (Postgres, MySQL/MariaDB, SQL Server, Oracle, Snowflake, Databricks, DuckDB, SQLite). Unchanged schemas are not read. Changed ones are refreshed table by table on Postgres, MySQL, SQL Server and Oracle (only new and changed tables are fetched; columns of changed tables are re-read when opened), and listed again elsewhere. A schema's Refresh button works the same way. Refresh on a connection first signs in again (the explorer's session and tabs that are not running a statement or in a transaction), so rights granted since the login show, including ones the server applies to new sessions only (Oracle roles).
  - In the background, the default catalog's schemas and the tables of the default and recently open schemas are listed, so clicking them doesn't wait. With "Choose schemas…"/"Choose catalogs…", the tables of every chosen schema (every schema of a chosen catalog) are listed too, one schema at a time, cache first, so autocomplete knows them without opening each.
  - Listings show in the explorer as soon as the server answers; saving them to the local cache (and reading the object versions used by the next refresh) happens afterwards in the background, in order.
  - Editing a connection's server, database, user or options clears its cache. Objects are grouped into Tables, Views, Materialized views, Functions, Procedures and Sequences (where the engine has them; every folder the engine has is shown, also when the schema has none, e.g. "No procedures"). Right-click a connection → "Choose catalogs…" (Databricks; databases on Snowflake/DuckDB, projects on BigQuery) or "Choose schemas…" (other engines) to list only some of the top-level items. Large schemas show 200 objects at a time with a filter box, so 10k-table catalogs stay responsive. Find tables with ⌘P: it searches every connected database, or one connection that you choose, with `schema.name` matching. Each match can be shown in the tree, inserted into the editor, or opened with a select of the top 100 rows. Right-click an object → "Show DDL" opens a read-only tab at once that loads the DDL (Format, Copy, Open in editor, Reload; Format shows it formatted in the connection's dialect and is remembered, Copy and Open in editor take what is shown): complete table DDL with keys, foreign keys, checks, indexes, partitioning and comments on Postgres, SQL Server and Oracle (Oracle's is read from the `ALL_*` views like DBeaver, so it works on other users' objects without SELECT_CATALOG_ROLE; views, materialized views, sequences, and code from `ALL_SOURCE`, packages and types with their body; DBMS_METADATA only as a fallback); the database's own DDL on MySQL (`SHOW CREATE`), Snowflake, Databricks, BigQuery, DuckDB and SQLite; functions and procedures on Postgres, MySQL, SQL Server and Oracle.
- **Local files:** query CSV/TSV, Parquet, JSON/NDJSON, Excel, Delta Lake and Iceberg with DuckDB. Use "Query a local file…" in the sidebar or palette, or attach files to a DuckDB connection (they appear as views in `files`). Excel: workbooks with several sheets ask for the first sheet or all sheets (connections have a "Read every sheet" option, one view per sheet); the whole used range is read, including columns under blank header cells (`column_D`) and rows after empty rows.
- **Editor:** CodeMirror 6 with dialect highlighting and schema autocomplete, run statement/selection/script, cancel, and error underlines. Collapse sections from the gutter (▾/▸; ⌥⌘[ / ⌥⌘] fold and unfold, ⌃⌥[ / ⌃⌥] all): statements, multi-line parentheses (subqueries, CTE bodies, column lists), `BEGIN … END` and `CASE … END` blocks, block comments and `-- region` … `-- endregion`; also in notebook cells and Show DDL. Parameters: write `:data_date` and a box for it appears above the editor; text is quoted for you (`2026-09-09` → `'2026-09-09'`), numbers (`2000`), `NULL`/`TRUE`/`FALSE` and already-quoted literals are kept, and the `{}` toggle in a box inserts an expression as typed (`current_date - 1`); hover a box to see what goes into the query. Notebooks get the same bar at the top, shared by all cells. Values are saved per tab; `::` casts, strings, comments and `col:path` are not parameters. Right-click (or ⇧⌥F) formats the selection, or the whole script when nothing is selected, in the connection's dialect (also in notebook cells). Autocomplete looks tables and columns up on demand, filtered by what you type (tables and columns you have already seen in the explorer, ⌘P or completion are cached locally across restarts and answer at once, along with the knowledge index; the server is asked in the background), so it never loads a whole schema or catalog and stays fast on 10k-table catalogs. Picking a table or view in FROM/JOIN also writes a short alias (`public.customer_orders co`; unique in the statement, skipped when an alias is already there). Functions and packages complete in expressions, procedures where they can be called (`BEGIN`, `CALL`, `EXEC`), and `pkg.` lists an Oracle package's functions and procedures; all inserted schema-qualified, ready to call (`app.fn_total(`).
  - Inline AI completion (Settings → Editor, off by default): after a short pause in typing, the AI panel's provider (its fast model when set) suggests the rest of the statement in grey at the cursor. Tab accepts it, ⌘→ accepts the next word, Esc dismisses it, typing what it says keeps the rest, and ⌥\ asks right away. The SQL around the cursor and a few relevant tables from the knowledge index are sent, under the connection's AI rules (AI off, providers not allowed, or a table rule that would hide a relevant table: no suggestion or no schema). Not with Kiro.
  - SQL snippets: type a prefix (`sel`, `selc`, `seld`, `ins`, `upd`, `del`, `with`, `join`, `lj`, `case`, `over`, `dup`) and pick it from the completion list; Tab and ⇧Tab move between its fields. Add your own in Settings → Editor (a prefix of a built-in one replaces it).
  - Transactions: while the tab's session has a transaction open (Postgres, MySQL/MariaDB, SQL Server, SQLite), the toolbar shows "Transaction open" with Commit and Rollback; closing such a tab asks first. "Auto-commit" switches the tab to manual commit: a write then opens a transaction that waits for Commit (DDL too, except on MySQL, which commits DDL at once).
  - Query plans: "Plan" in the toolbar opens the plan of the statement at the cursor (or the selection) in a tab, as one tree for every engine (Postgres, MySQL/MariaDB, SQLite, DuckDB, SQL Server, Oracle, Snowflake; Databricks as text) with cost and estimated rows per step. Analyze (Postgres, MySQL, DuckDB; read queries only, as it runs them) adds actual rows, loops and time; the slowest step, full scans of many rows and estimates off by 10× or more are marked. It runs on the tab's session with its `:name` values.
  - Files: ⌘O opens a `.sql` file in a tab (recent files are in the palette), ⌘S saves it back, ⇧⌘S saves any tab to a file. A file changed by another program reloads when DataBrain gets focus (or asks, when the tab has unsaved edits), and a save never overwrites such a change without asking. File tabs come back after a restart.
  - Query tips for slow queries (all engines): when a statement runs longer than the slow-query threshold on the server (time spent downloading a finished result from Databricks/Snowflake cloud storage doesn't count, and a statement that is only downloading is not checked) (Settings → Queries, default 60 s; 0 turns tips off), DataBrain reads the indexes, partitions and cluster keys of its tables on a separate session while it keeps running, and lists ways to make it cheaper above the result (refreshed when it ends; faster queries get no tips) (no partition filter, a function or cast on a partition/indexed column, `LIKE '%…'` on an indexed column, a filter no index covers on a large table). Click a tip to select the spot in the editor, or "Improve with AI" to have the assistant rewrite that statement (it gets only the statement, its tips and its tables' indexes/partitions/cluster keys, and the rewrite is shown as a diff to accept); the ran statement is underlined with the reason on hover, and table names show their layout. Autocomplete lists key columns first (`partition key`, `cluster key`, `primary key`, `indexed`).
- **Lineage:** column lineage of SQL, drawn as a diagram in a read-only tab.
  - Open it with "Lineage" in the editor toolbar, or right-click → Show lineage (also in notebook cells). It traces the selection, or the whole script when nothing is selected. Refresh re-reads the editor.
  - A script of several statements opens as a **Chain**: only its tables and results, one line per table-to-table flow across the statements (through any CTEs and subqueries), so `insert into a … from src; update b … from a; create table c as select * from b; merge into d using c …` reads src → a → b → c → d. Hover a line for the statements it goes through; click a table for its column lineage. "Columns" switches to the full column view (the default for one statement).
  - The column view starts at table level, one line per link between tables. Click a table to list its columns ("All columns" lists every table's), click a column to trace it: its path is highlighted and the tables on it show the columns it uses.
  - The right panel shows the traced column as a top-down flow: the column, an arrow with its expression (and the joins/filters where several inputs meet), then its input columns side by side, down to the database tables. Below it, the column written in database columns (`total = sum(sales.orders.amount * sales.orders.rate)`). The panel can be resized, ↗ opens the flow in a tab of its own, and clicking an expression or join selects it in the SQL.
  - The controls at the bottom right zoom in (+) and out (−) and switch the layout between left to right and top to bottom (also ⌘/Ctrl + scroll to zoom). Drag tables around (view only; Reset layout puts them back). Export to draw.io, Mermaid (or copy it), Graphviz DOT, SVG, PNG or JSON, as laid out on screen (Mermaid and DOT keep the direction, not moved positions).
  - "Check with database" (on with a connection): uncached tables are described, and each read query is checked with `EXPLAIN`, never run, on Postgres, MySQL, DuckDB, SQLite and Snowflake. Errors show in the header with their position; writes and DDL are skipped; offline, the diagram still works from the explorer cache. `:name` parameters use the values entered.
  - **Covered:** SELECT with joins (inner, left, right, full, cross, semi/anti, `ON`, `USING`), `WHERE`/`HAVING`/`QUALIFY`, `GROUP BY` and aggregates, window functions, `CASE` and other expressions, subqueries in `FROM` (including `LATERAL`), in the select list and in `WHERE`/`EXISTS`/`IN`, CTEs, `UNION`/`INTERSECT`/`EXCEPT` (by position), `VALUES`, `UNNEST`, `SELECT *` and `alias.*` (from the explorer cache or a describe), quoted identifiers per dialect. Scripts: `CREATE TABLE … AS`, `CREATE VIEW … AS`, `INSERT … SELECT`, `SELECT … INTO`, `UPDATE … SET … FROM` (and MySQL `UPDATE a JOIN b`), `DELETE … USING` (and MySQL `DELETE t FROM …`), `MERGE … USING … WHEN MATCHED UPDATE / WHEN NOT MATCHED INSERT` and plain `CREATE TABLE (…)` / `CREATE TEMP TABLE` link statements, so a table written by one statement is the one a later statement reads (also when one names it `tmp` and the other `public.tmp`). `TRUNCATE`, `DROP` and `ALTER TABLE … ADD COLUMN` are understood; a table created again gets the new columns, `IF NOT EXISTS` keeps an existing table's. Each step is marked copied, computed, aggregated, filter or join. Unknown columns, ambiguous names and columns that can't be placed are listed under "N not traced", never guessed.
  - **Not covered (yet):**
    - `WITH RECURSIVE` is only traced when the CTE has a column list (`t(n)`); without one, the recursive step's columns are not resolved. Recursive CTEs written without `RECURSIVE` (SQL Server, Oracle) are not recognised, and Oracle `CONNECT BY` is ignored.
    - Procedural blocks (`BEGIN … END`, `DECLARE`), `COPY`, `ALTER TABLE … RENAME` and other statements: only their tables are shown. Statements the parser rejects (some PL/SQL and vendor syntax) are shown the same way and marked partial. `WITH … UPDATE/DELETE` is not traced.
    - One box per table for the whole script: a table read, then dropped and created again, is one box, and a table feeding itself (`INSERT INTO t SELECT … FROM t`, a self-join `UPDATE`) draws no line.
    - `PIVOT`/`UNPIVOT`, table functions, `JSON_TABLE` and similar sources appear as a box without column lineage. A subquery in the select list is linked through its first column only.
    - Database views are not expanded: a view is a box like a table.
    - `SELECT *` on a table whose columns are neither cached nor reachable shows one `table.*` line. An unqualified column with two such tables in scope is not assigned.
    - No `EXPLAIN` check on SQL Server, Oracle, Databricks and BigQuery. The check only reports errors; it doesn't correct the lineage. A statement that reads a table created earlier in the same script may be reported as failing.
    - One editor, selection or notebook cell at a time: no lineage across saved queries, notebooks or the workspace, and no lineage recorded by the server (Unity Catalog, Snowflake access history, BigQuery).
    - Expressions are shown as the parser prints them (normalised spacing); the database-columns formula stops expanding past about 240 characters.
    - Lineage tabs, moved tables and expanded tables are not kept after a restart.
- **Notebooks:** SQL and Markdown cells on a connection.
  - Run a cell, run all, or run from here.
  - Output stays under each cell, and all cells share one session.
  - Per-cell connection override and AI actions. Notebooks are saved and can be put in folders.
- **Jobs:** SQL steps that run in order, by hand or on a schedule (sidebar → Jobs).
  - A job opens in a tab as a canvas of steps. Drag steps around; drag a step's ● handle onto another step so it runs after it (or onto empty space to add one there). Click a link and press Delete (or right-click it) to remove it. Selecting a step highlights everything upstream and downstream of it.
  - "Create job" at the top of a notebook makes a job with one step per SQL cell, top to bottom, each running after the cell above, on the cell's connection (or the notebook's). Steps are named after the cells' output names; as those names belong to the notebook, a step gets the next free name (`revenue_2`) and `results.revenue` in later steps is renamed to match. Markdown and empty cells are skipped; `:name` parameters are not filled in.
  - Each step does one thing, its action, shown at the top of the side panel (resizable): run a query (a connection and SQL, with the usual completion and formatting), load into a connection, or save to a file. Load and save steps take all rows of their upstream step unless you choose "Filter or reshape with SQL…" (a DuckDB query). Changing the action asks first and removes the old action's settings, so a step never carries a query, a load target and a file at once (the app drops them on save too). "Copy from a query tab" (or right-click the canvas → From a query tab) takes a tab's SQL and connection.
  - A step's result is an output named after the step, and the step owns that name: no other step (in any job) can have it, and query tabs, notebook cells and renames can't produce `results.<step>` (the step-name box says what already uses a name). A name is free again when the step is renamed or deleted. Steps on Results (DuckDB) read upstream outputs as `results.<step>`, so they can combine several connections; renaming a step renames it in the SQL of the steps that read it, and a step that reads `results.x` without running after `x` gets a "Link" warning.
  - Right-click a step: Run this step, Run from here (it and everything downstream), add a step after it that queries its output (DuckDB), loads it into a connection, or saves it to a file, View output, Duplicate, Delete.
  - Load steps select rows with DuckDB (by default `select * from results.<upstream>`) and write them into a table of any connection. Modes:
    - Insert: a missing table is created from the rows' column types when "Create the table if it's missing" is on (the default); the run shows a notification and the step lists the columns it created. Off, a missing table fails the step before anything runs.
    - Delete rows, then insert: the same, after `DELETE FROM` the table.
    - Replace table: drop it and create it again from the rows' columns (`NOT NULL` where the rows have no NULLs by type), then insert.
    - Update by key and Merge (upsert) by key: the table must exist, and you name the key columns. The rows go into a staging table with the table's own types, then one `MERGE` (SQL Server, Oracle, Snowflake, Databricks, BigQuery) or `UPDATE … FROM`/`JOIN` plus `INSERT … WHERE NOT EXISTS` (Postgres, MySQL, SQLite, DuckDB). Update ignores rows without a match; Merge inserts them. The step's rows are those the database reports as updated or merged.
  - The rows' columns are matched to the table's by name, ignoring case (`id` loads into Oracle's `ID`); a column the table doesn't have fails the step and lists the table's columns.
  - Target check: while you choose the connection and type the table (here and in the result grid's "Load into…"), the path is checked part by part against the database: the catalog/database (Snowflake, Databricks, BigQuery, DuckDB, SQL Server without a database set), the schema (the connection's default when you write only the table, shown as e.g. `main.people`) and the table. A missing catalog or schema shows a red box saying to create it first, with the SQL to do it (`CREATE SCHEMA …`, `CREATE DATABASE …`, `ATTACH …`) to copy; only the table is created for you. A name typed in another case is accepted and the database's spelling is used: `account` loads into an existing `ACCOUNT` (Snowflake, Oracle, Postgres `"Account"`…), and the check says so; when two names differ only in case, type the exact one. A new table keeps the name as typed. A view, too many name parts, or a table missing in Update/Merge (or with "Create the table" off) are flagged too, and "Load into…" can't start until it's fixed. Quoted parts can be typed (`"My Schema".t`, `[dbo].[t]`, `` `project.dataset.table` ``). A load (or dry run) whose catalog or schema doesn't exist stops before anything is created, with the same message; with before SQL it isn't stopped (it may create them).
  - Before SQL and After SQL run on the target connection around the load (several statements allowed), for example to delete a day's rows first or to refresh a summary after. A missing table is accepted when there is before SQL (it may create it).
  - Postgres, SQLite, DuckDB and SQL Server run the whole step, before and after SQL included, in one transaction: a failure rolls everything back. MySQL does too unless the step has DDL (which MySQL commits at once). Oracle, Snowflake, Databricks and BigQuery commit statement by statement; the error then says that what ran before was kept. INSERTs are built one at a time while the rows are sent.
  - Batch size: "Rows per INSERT" and "Max KB per INSERT" set how big each INSERT is; a statement ends at whichever comes first. Empty uses the connection's default (500 rows, 100 on Oracle; 1 MB). Values above the connection's maximum are lowered, with a note in the run log and the dry run: SQL Server 1,000 rows (its VALUES limit), Oracle 1,000 rows, others 10,000; SQLite, BigQuery and Snowflake 1,000,000 bytes of SQL text, MySQL and Databricks 16 MB, others 64 MB. One row larger than the byte limit still goes in a statement of its own.
  - Dry run (in the load panel) checks the step without keeping any change: the step's SQL selects up to 1,000 rows, then, where the step runs in a transaction, every statement really runs on those rows and is rolled back; elsewhere each statement is checked with `EXPLAIN` where the database has it (MySQL, Snowflake), and DDL and the rest are listed as not checked. It reports whether the table exists, whether it would be created, and each statement's result. An upstream step that hasn't run yet is reported, and the statements that don't need the rows are still checked.
  - Save-to-file steps select rows the same way and DuckDB writes them (`COPY … TO`) as CSV (with a header), Parquet (zstd) or JSON lines into a folder you choose (Downloads by default; a missing folder fails the step before it runs). Leave the file name empty for a new name per run (`{step}_{date}_{time}`), or give one, with `{step}`, `{job}`, `{date}`, `{time}` filled in; a fixed name is overwritten on each run. "Show file" reveals the last file in Finder/Explorer.
  - Steps that don't depend on each other run at the same time; when a step fails, the steps after it are skipped and the others still run. Each step shows its status, rows and time, and the job panel lists recent runs with each step's outcome (the last 200 are kept). Stop cancels the running statements.
  - Run log: every run keeps a log for tracing: when it started and why, each step starting, skipped or cancelled, every statement it ran (before SQL, the query, create/delete/drop, each group of inserts, update/merge, after SQL, commit or rollback) with its SQL, rows and time, server notices, created tables, and each error with the statement that failed. It shows live while the job runs (following new lines), under each run in the job panel and per step in the step panel; filter it by step or to errors and warnings, open any line's SQL, or copy it as text. Up to 5,000 lines are kept per run.
  - Load progress: while a load step inserts (or stages rows for update/merge), its card and panel show a bar with the rows written so far out of the total, updated after each INSERT batch.
  - Schedule: every N minutes, or at a time of day on chosen weekdays (local time). Schedules run while DataBrain is open; a run missed while it was closed runs once at the next start (a few seconds after launch). To keep them running when DataBrain is closed, turn on Settings → Jobs → "Also run them when DataBrain is closed" (off by default): the computer then starts `databrain-jobs tick` every minute while you are logged in (a launchd agent on macOS, a systemd user timer on Linux, a Task Scheduler task on Windows), which runs the due jobs and exits; failed runs show a desktop notification. A job runs in one process at a time (a lease in the workspace), so the app and the runner never run it twice, and runs the runner is doing show as "running in background". Connections with browser sign-in fail in the background once their sign-in expires. From a terminal, `databrain-jobs run <job>` runs a job now (exit code 1 when it fails) and `databrain-jobs list` lists them; the binary is next to the app (`DataBrain.app/Contents/MacOS/` on macOS). Each scheduled run shows "Starting scheduled job …", a failed one shows a notification, and the Jobs icon in the sidebar has a red dot while any job is scheduled.
  - Runs don't ask for confirmation, also on production connections (the load panel warns about those); read-only connections are refused. `:name` parameters are not filled in for job steps.
- **Outputs:** every result gets a handle (`r12`), and you can also give it a name (`revenue`).
  - Query outputs together with DuckDB as `results.<name>`, including joins across databases (Postgres × Snowflake × CSV…).
  - A rerun keeps the previous version as `revenue__1`. Compare versions or any two outputs (rows added, removed or changed) and chart any output. Columns are matched by name (also ignoring case); in the compare dialog each column of the after output has a list to pick its before column (`a` ↔ `a1`, `b` ↔ `b2`, …), to override an automatic match or to leave it out, and several pairs can be typed at once (`a = a1, b = b2`, `r1.a -> r2.a1`).
  - @mention outputs to the AI.
  - Pin outputs to keep them across restarts (saved as Parquet in the app-data `outputs/` folder).
  - History links to each output. Queries run by the AI assistant (or an MCP client) are hidden there by default; the ✨ button in the History header shows them, marked "AI"/"MCP"; job steps are marked "Job". The list shows the latest 50 and loads more as you scroll. The 🗑 button deletes queries run by the AI (the default), those older than a number of days, or everything; the results they produced are deleted with them (pinned outputs and results still shown in a tab are kept). Each entry has a delete button (its result goes with it). History older than 30 days is deleted automatically, with its results (Settings → Queries → History: another number of days, or never). AI conversations not continued for 30 days are deleted the same way, with their own setting there. Capped outputs warn when they are queried.
  - Notebook cells can name their output; later cells read it, and cells whose inputs changed are marked stale.
- **Results:** virtualized grid, sort, filters, find, column stats, copy. Click a column name to select (highlight) the column (⇧/⌘ to add columns); double-click it to sort (⇧ adds a sort key), or sort from its ▾ menu. Point at a column name to see its type as the database names it (`character varying(255)`, `numeric(12,2)`, `NUMBER(10,0)`, `datetime2`), not the internal Arrow/DuckDB type; for Results (DuckDB) queries over outputs, also the type the column has in each `results.<name>` it comes from. Export to CSV, TSV, JSON, NDJSON, Markdown, SQL INSERT, Parquet or XLSX. Export the current view, all fetched rows, or all rows of the query ignoring the row limit: the statement runs again on its own session and every row is written straight to the file (only read queries). That full export runs in the background: the dialog shows its progress (connecting, running, downloading, rows written, file size, time) with "Run in background" and Stop, and once sent to the background it stays at the bottom right with Stop while running and Show file when done, so you can keep working (several can run at once).
  - Saved views (Views in the result toolbar): save the current column filters, sort and quick filter under a name, for the result's table or for any result with those columns, and apply them later. Columns are kept by name, so a view still applies when a query returns its columns in another order; columns a result doesn't have are skipped (and named). The quick filter of a query on one table (Select top 100 rows, `SELECT … FROM t WHERE …`) is remembered for that table and filled in again the next time its rows are shown; clear it to forget it. Both are kept in settings (the newest 200 views and 300 tables).
  - Editing: "Edit" on a result of a query on one table with a primary key changes cells, adds and deletes rows. While it checks the table (schema, columns, primary key; from the explorer's cache when it has them) a "Checking … before editing" bar shows and Edit can't be clicked again; Preview SQL shows the statements, Save runs them all or nothing (a transaction; one PL/SQL block on Oracle), and each UPDATE/DELETE must hit exactly one row. Inside an open transaction the changes join it.
  - Foreign keys: right-click rows of a single-table result → "Open referenced …" (the table's own keys) or "Rows in … referencing this" (keys that point at it, from the knowledge index or the table's schema); the query opens in a new tab.
  - Value panel ({} in the result toolbar, ⇧Space or "View value"): the selected cell's whole value, JSON as a tree, XML indented, binary as a hex dump or as the image it holds, long text wrapped; editable while editing.
  - Charts: bar, line, area, pie and scatter. "Pin to dashboard" keeps a chart and its query in a dashboard (open it from the palette); a dashboard runs its charts' queries again when opened, each with Refresh.
  - Large cloud results: when Databricks (external links) or Snowflake (result chunks) hands a large result out as files in cloud storage, a notice says so while it downloads ("The data is large (1.4 GB, 3200000 rows in 52 chunks), so it is downloaded from Databricks's external links: https://…/results_0?…"; the link's signature is not shown), and the run shows how long the query took on the server.
- **AI mode** (⌘L panel, ⌘I inline edit):
  - Providers: Kiro (browser sign-in or `ksk_` API key, through `kiro-cli`), OpenAI, Anthropic, Gemini, Azure OpenAI, OpenRouter (browser sign-in), Ollama, LM Studio, or any OpenAI-compatible server.
  - The assistant uses indexed schema metadata plus your notes/glossary as knowledge. Indexing is incremental: one cheap catalog query per run tells which schemas changed (Postgres, Oracle, MySQL/MariaDB, SQL Server, Snowflake, Databricks Unity Catalog, DuckDB, SQLite), and only those are re-read; "Rebuild" re-reads everything. Postgres, Oracle, MySQL, SQL Server, Snowflake and Databricks read a whole batch of schemas with a few catalog queries instead of several per schema. BigQuery re-reads every dataset. When a question names a table the index doesn't have, the assistant doesn't ask you for its columns: it asks to index that table ("Index these tables?", up to 20 at a time; only the structure is read, no rows), adds it to the index without touching the rest, and continues with it. While exploring it records what it learns (code meanings, business rules, join paths) and updates outdated notes; changes wait for review in Knowledge unless the connection's "Save AI notes directly" is on.
  - A note can be about one or more tables of the connection (`sales.orders`, `sales.orders.status`, or `sales.orders & crm.customers` for join knowledge; `and`, `or` and `,` also separate tables). The field completes table and column names, and only tables that exist are accepted (checked against the knowledge index, then tables already seen in the explorer, ⌘P or autocomplete, then the live connection, which gives up after 10 s if it is busy indexing) — for notes you write, notes the AI writes, and imports.
  - Share notes: Knowledge → Export… writes a `.databrain-notes.json` file; Import… shows new notes, ones you already have, and ones that differ. For each difference, keep yours, use the file's, keep both, edit a merge, or let the AI merge them. It proposes SQL as diffs, runs queries after approval (per-connection policy), and analyzes results.
  - Several connections: the connection name under the question box opens a picker. Tick other connections (with AI on) and the assistant gets their relevant tables too, and can list, describe and query them (`run_query` takes a connection; each keeps its own policy and approvals), then combine the outputs with DuckDB. The choice is kept across restarts. `list_connections` shows what it may use.
  - Usage and budget: under the question box, the conversation's tokens (Kiro: credits spent and how full the context is) and the provider's budget where it reports one: Kiro's plan credits (used of the allowance, reset date), OpenRouter's account credits and the key's spend and limit, DeepSeek's balance. Click it (or Settings → AI providers) for details, tokens used today and this month, and the provider's billing page. OpenAI, Anthropic, Gemini, Azure and local servers don't report a balance for an API key, so only tokens are shown for them.
  - Table access (connection → AI → "Tables the AI may use"): which tables the assistant may read and write, as SQL LIKE patterns: "AI read access: like" (`'catalog_read%', '%schema_can_read%'`), "not like" (`'cannot_read%'`), and the same for writes (with writes allowed). Patterns are not case-sensitive and match `catalog.schema.table`, `schema.table` or `table`; unqualified names in the SQL get the connection's default database and schema; an empty "like" list means every table, and "not like" always wins. The SQL is parsed to find every table it reads (joins, subqueries, CTEs, `INSERT … SELECT` sources) and writes (`INSERT`/`UPDATE`/`DELETE`/`MERGE` targets, `CREATE`/`ALTER`/`DROP`/`TRUNCATE`); MongoDB commands count their collections, `$lookup`/`$unionWith` and `$out`/`$merge` included. It applies to the assistant's queries, sample rows, results it reads (a result of your own query on a denied table, or one combined from it on DuckDB, stays hidden), jobs it creates, changes or runs (query steps and load targets), and to MCP clients; the assistant is told the rules. While rules are set, SQL whose tables can't be told (procedure calls, SQL the parser rejects, Neo4j Cypher) or that changes the default schema (`USE`, `SET search_path`) is refused; a name whose catalog or schema isn't known (no default set) must be written in full when a pattern needs it. "Try a table" in the dialog shows whether a name may be read and written.
  - Auto-approve (the shield next to the connection under the question box): approves every request of the current conversation without asking: queries (writes too), job changes and runs, and editor changes, including those already waiting. It is shown as "Auto" while on, and cards say "Auto-approved". It is per conversation: a new conversation, or one opened from History, asks again. Connection policies still apply (a read-only connection still refuses writes).
  - Several conversations at once: each is a tab under the panel's header (New chat adds one; opening a History entry opens it in a tab, or shows its tab if it is open). They work at the same time, each with its own question queue, approvals, auto-approve and usage; a tab shows a spinner while it works, a shield when it waits for your approval, and a dot when it answered in the background. Closing a working tab asks first and stops it; the conversation stays in History. Open tabs and unsent questions are kept while switching, and the tabs come back after a restart (up to 12; the oldest idle one closes for a new one). "Ask AI" in a dialog uses a conversation of its own, so it doesn't wait for another one.
  - Fix/Explain/Analyze buttons; conversation history; audit log. Fix with AI works on the statement that failed, not the whole script: it is selected in the editor, sent to the assistant as the failed statement (with its line), and the fix replaces only it.
  - Jobs: the assistant lists and explains jobs (steps, connections, SQL, last run errors) and creates new ones from a description, after you approve its plan. It can look up tables on any AI-enabled connection, so a job can read from several databases, combine them in a Results (DuckDB) step over `results.<step>`, then load the rows into a table or save a file; links between steps are added for `results.<step>` it reads. The new job opens in a tab; it is not run until you run it. It also changes and fixes existing jobs: it reads the latest run's errors with the failing statement, tests a corrected query, and proposes the change (what changes is shown for approval); steps it keeps keep their place on the canvas and their history, renamed steps are renamed in the SQL that reads them, and an open job tab shows the new version. It can also run a job (or some of its steps) after you approve the run (the card says which tables and files it changes), waits for it, and reads the outputs; runs it starts are marked "by AI". Asked to compare or check data across connections, it queries each and compares the outputs for a quick look, and proposes a job (one step per connection, a Results step that compares them, optionally a load or file) when you want it repeatable, saved or scheduled. Steps whose SQL the assistant wrote run under the same DuckDB sandbox as its queries whenever the job runs (by hand, on the schedule, in the background), until you change their SQL yourself or click "Trust this SQL" in the step's panel, which says the AI wrote it. Jobs the assistant made before steps recorded this are found once in the audit log (by job name) and marked.
- **MCP:** `databrain-mcp` (stdio) exposes opted-in connections to Kiro CLI, Claude Code, Cursor… (Settings → MCP / Kiro shows the config snippet). The connection's AI rules apply (read-only and production connections refuse writes, writes must be allowed, queries can be turned off). What DataBrain would ask the user about, it asks through the client with MCP elicitation (the question and the SQL; only an explicit approve runs it; the client is told it is waiting when it gave a progress token). No answer within 2 minutes (`DATABRAIN_MCP_ELICIT_SECS` changes it) ends the call with a message that says what to change, and no further question is asked in that session: a client can declare elicitation and still not show prompts in some modes. A client without elicitation gets a refusal instead, because its own tool approval isn't DataBrain's question and many clients approve tools on their own; a connection can accept it anyway with "Accept the MCP client's approval" (audit log: "approved by MCP client"). Changes that need confirmation in DataBrain itself are never approved over MCP. When the client cancels a call, DataBrain stops waiting for the answer and cancels its running query.
- **Schema compare:** right-click a schema → "Compare with another schema…" (or the palette): tables, views and routines on one side only, and per table the columns added, removed or changed (type, NULL, default), primary key and foreign keys, across connections and database types. The script that makes the target like the source (in the target's dialect, DROPs as comments) opens in an editor to review; nothing runs by itself.
- Safety prompts for prod and for writes, read-only connections, saved queries, history, command palette (⌘K; it also lists jobs to open, run or stop, plus New job and Show jobs).
- **Appearance** (Settings → Appearance): dark/light theme; background presets (Default, Graphite, Slate blue, Forest, Warm paper, High contrast; each with a dark and a light version) or a custom colour, from which panels, borders and readable text are derived; interface font and code font (editor, result grid, SQL) from common fonts (marked when not installed) or any installed font by name; code font size (10–22 px).

## Runtime notes

- Oracle needs no Oracle software by default: the thin driver (a small helper using [go-ora](https://github.com/sijms/go-ora), Oracle 10g+, TLS/wallets, native network encryption via "Driver options") is downloaded on the first Oracle connection (about 5 MB, into the app-data folder `oracle-agent/`, checked against SHA-256 sums built into DataBrain). Where the network blocks that download, the connection's Driver section shows the link and its SHA-256: download the `.gz` another way and use "Install from a downloaded file…" (the `.gz` or the unzipped file; only a file matching the built-in sum is accepted). Choose the "Oracle Instant Client" driver on a connection for thick-only features; DataBrain then checks for Instant Client and can install Oracle's Basic package in one click, checked against the SHA-256 Oracle publishes (into `oracle/instantclient_*`; Linux also needs `libaio`).
- SQL Server connections use rustls for TLS (TLS 1.2 and 1.3), the same on every OS; macOS's own TLS library broke off the handshake with some servers. SQL Server 2014 and older without the TLS 1.2 update only offer TLS 1.0/1.1: update the server, or set SSL to Disable.
- Google/Snowflake/Entra browser OAuth needs your own OAuth client ID.
- DuckDB is compiled into the app (with Parquet and JSON). Its Excel, Delta, Iceberg, Avro, httpfs and ICU extensions are downloaded at build time and shipped inside the bundle, so nothing is downloaded at runtime.
- Without bundled DuckDB ("no-duckdb" downloads, `DataBrain-no-duckdb_<version>_…`): for computers that already have DuckDB. The app is about 85 MB instead of 290 MB on macOS and uses the DuckDB library installed on the computer (`libduckdb.dylib`, `libduckdb.so` or `duckdb.dll`, DuckDB 1.5 or newer; the CLI alone is not enough), loaded at startup from Homebrew's and the usual install folders, `DATABRAIN_DUCKDB_LIB`, or the file chosen in Settings → DuckDB engine. Extensions come from DuckDB's own folder (`~/.duckdb/extensions`) and are installed on first use. The app starts without the library: a banner explains how to install it (`brew install duckdb`, or libduckdb from duckdb.org), lets you choose the file or look again, and links to the download with DuckDB included; until then Results, outputs, jobs that combine connections, local files and DuckDB connections say the engine is missing.
- Terminal (Settings → Terminal): CLI sign-ins that need a terminal (`kiro-cli login`) open the one chosen there. The list shows the terminals found on the computer (macOS: Terminal, iTerm, Ghostty, WezTerm, Alacritty, kitty apps; Windows: cmd, Windows PowerShell, PowerShell 7, Windows Terminal, Git Bash, WezTerm, Alacritty in their install folders or on PATH; Linux: well-known terminals on PATH plus any `.desktop` entry in the TerminalEmulator category; Rescan looks again), plus Automatic (tries them in order), a custom command (`{script}`, `{sh}`, `{cmd}`, `{ps1}` are filled in), or none. A terminal that doesn't run the command within a few seconds counts as blocked (for example PowerShell blocked by IT): Automatic tries the next, and in the end the sign-in dialog shows the command to copy and run yourself, and waits for it. PowerShell gets the command with `-EncodedCommand`, so script execution policies don't stop it. Test opens the chosen terminal once.
- Kiro needs Kiro CLI installed (`curl -fsSL https://cli.kiro.dev/install | bash`). API keys require a Kiro Pro plan or higher. DataBrain writes one agent config, `~/.kiro/agents/databrain-sql.json`, which limits Kiro to DataBrain's tools.
